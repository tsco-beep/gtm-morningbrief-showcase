Technical overview

Morning Brief — technical overview

How the Morning Brief agent works end to end: the architecture, the daily pipeline, the agents and their guardrails, the conversational copilot that turns insight into action, the security posture, and a phased plan to deliver it.

Prepared by  Taylor — GTM / Revenue Enablement Audience  CTO / engineering leadership Status  Design complete · interactive mock live

01Approach

The system is delivered as a loop, not a big-bang. Each agent or workflow is shipped through the same five steps, and the whole system is delivered in thin, demoable slices so value shows up early and integration risk stays low.

The loop, per workflow: Job → Tools → Guardrails → Eval → Iterate. Define the one job, give it the minimum tools, decide what it must never do, write the test cases before building, then iterate until it passes.

Delivery order (thin slices):

  • A  Mock on fake data — prove the output and UX. (done — see the dashboard)
  • B  Scripted prototype — real scoring logic on a CSV export, no live APIs.
  • C  Wire one source (Salesforce read) end-to-end to Slack for one rep.
  • D  Add the news agent + LLM assembly, then the dashboard read-API.
  • E  Pilot with 5–8 reps, tune weights, then roll out.
Design principle: the daily agent is read-only and advisory. Any write action runs through the copilot (§09), which acts as the signed-in user with explicit confirmation — so the riskiest scopes are never granted to an autonomous background job.

02System architecture

Five sources feed a scheduled orchestrator, which runs three processing jobs into a store that two surfaces read from.

03The morning run (pipeline)

One scheduled job per rep, finishing before the workday starts. End-to-end is a few minutes.

  1. Pull — fetch each rep's open opps, activities, contacts, today's calendar (read-only).
  2. Score — deterministic risk + momentum per opportunity (§06).
  3. Scan news — the browser agent checks each top account's signals overnight (§07).
  4. Summarize — LLM writes the "so-what" for news and the recommended actions, grounded in the pulled data only (§08).
  5. Assemble — build the per-rep brief object: top-5, risk watchlist, follow-ups, heating-up, day plan.
  6. Deliver — post the concise Slack brief and write the full brief to the store for the dashboard.

04The four workflows

Each is a discrete job with one responsibility, its own tools, and its own guardrails — so they can be built, tested, and swapped independently.

① Account scoring deterministic

Compute a risk score and a week-over-week momentum delta for every open opportunity.

In: opps, activities, stage history, engagement · Out: {account_id, risk, momentum, reasons[]}
Guardrail: pure + explainable — every score carries the signals that produced it. No LLM here, so it's reproducible and testable.

② News & signals agent browser

Browse the web for each top account, extract relevant events, match them to accounts and open opps, and attach a source link.

In: account names + domains · Out: {account_id, headline, type, source_url, ts}
Guardrail: every item must carry a real source URL or it's dropped. No fabricated or unsourced news.

③ Brief assembly LLM

Rank items into a top-5, write each "so-what" / recommended action, and produce the brief in a fixed JSON schema — grounded only in retrieved data.

In: scores + news + opp facts · Out: brief.json (validated)
Guardrail: grounded generation only — the model may not invent deals, numbers, or contacts. Output is schema-validated; failures fall back to deterministic text.

④ Delivery integration

Render the concise brief into Slack Block Kit and post it; persist the full brief for the dashboard read-API.

In: brief.json · Out: Slack message + stored record
Guardrail: idempotent — re-running a day doesn't double-post. Delivery never mutates source systems.

06Scoring engine

Two transparent, tunable scores. Deterministic so they're testable and an AE can trust them.

Risk score (0–100)

SignalWhyWeight
Days since last activitySilence is the top slip predictor0.30
Close date vs. stageNear close but early stage = danger0.25
Days stalled in stageStuck deals quietly die0.20
Champion engagement decayOpens/replies trending down0.15
Single-threadedOne contact = one point of failure0.10
def risk_score(opp):
    s = (0.30*norm(opp.days_since_activity)
       + 0.25*close_vs_stage(opp)
       + 0.20*norm(opp.days_in_stage)
       + 0.15*champion_decay(opp)
       + 0.10*(1 if opp.single_threaded else 0))
    return round(100 * s), reasons(opp)   # always return the "why"

Daily priority ≈ risk × deal_amount (impact × urgency), capped at 5. Momentum is the change in the account fit/intent score vs. last week — surfaced as "heating up."

07News & signals agent (Browserbase)

This is the "browse the web for what changed" job. Browserbase provides managed headless Chromium sessions, so the agent can load real pages (news, press, LinkedIn, the account's own site) and extract structured events — then an LLM pass normalizes and attributes them.

Flow

  • Target — for each top account, build queries from name + domain (funding, exec changes, layoffs, launches, earnings).
  • Browse — open a Browserbase session, run the searches, load result pages, capture text + URL.
  • Extract — LLM turns raw page text into {type, headline, source_url, ts}; drop anything without a source.
  • Match & dedupe — link each signal to an account (and flag if it's an open opp); dedupe against the last N days.
  • Persist — write to Signal; the brief highlights signals tied to open opportunities.
Guardrails: source URL required · respect robots/ToS and rate limits · cache results to avoid re-browsing · never store credentials in code.

Why a browser and not just a news API: coverage of long-tail e-commerce accounts and primary sources (the company's own site, a press page, a LinkedIn post) that news APIs miss. Browserbase handles the headless infra, proxies, and session scaling so the agent code stays small.

08LLM layer & prompt design

The LLM does narrow, grounded jobs only: summarize a call/news item, write a "so-what," and phrase recommended actions. It never decides risk (that's deterministic) and never invents facts.

Prompt structure (CLEAR, inside a strict schema)

System: You write a seller's morning brief. Use ONLY the JSON facts
        provided. Never invent deals, numbers, names, or news.
        If a field is missing, say so. Output must match the schema.

Facts:  { opps:[...], scores:[...], signals:[...], calendar:[...] }

Task:   Rank the top 5 by impact×urgency. For each, one-line reason
        + one recommended action. Keep the Slack version < 150 words.

Schema: { priorities:[{account_id, reason, action}],
          risk:[...], followups:[...], heating_up:[...] }
  • Grounding — facts are injected; the model can't reach outside them. Unsupported claims are a test failure.
  • Structured output — JSON schema-validated; on validation failure, fall back to deterministic templated text so a rep always gets a brief.
  • Determinism — low temperature; the brief should be stable for the same inputs.

09Conversational copilot (action agent)

Everything above is read-only insight. The copilot is the layer that turns the brief into action — a chat assistant embedded in the dashboard that can draft a follow-up, update a deal, create a task, or book a meeting on the user's instruction. It is the only component that writes to source systems, and it does so as the signed-in user, with confirmation.

How it works

It's a tool-calling agent. Each action the company wants to allow is registered as a tool — a thin wrapper around one scoped API call (e.g. update_opportunity, draft_email, create_task). The user types a request; the agent plans, calls the needed tools, and returns results. Read tools run directly; write tools are proposed for confirmation first.

Read tools execute directly; write/external tools are proposed and require user confirmation. All actions run as the user and are logged.

Identity, SSO & permissions

The copilot never gets a broad service account. It acts on-behalf-of the signed-in user:

  • Authentication via your IdP — the user signs in through the company's existing SSO (Okta / Entra, SAML or OIDC). The app receives a per-user, delegated token (OAuth 2.0 on-behalf-of / token exchange).
  • Authorization is inherited — every tool call uses that user's token, so the agent can do only what the user can already do. Existing CRM profiles, field-level security, and RBAC apply unchanged. No privilege escalation.
  • Least-privilege scopes — the OAuth app requests only the scopes the registered tools need; anything outside the tool registry is simply not callable.
  • No standing access — tokens are short-lived and refreshed; the agent holds no long-lived credentials.

Safety & governance

  • Human-in-the-loop writes — every write or external action (CRM update, email send, calendar change) is shown as a proposed action the user approves in the chat. Drafts are never sent automatically; irreversible or bulk actions always confirm.
  • Full audit trail — every tool call is logged with user, action, parameters, and before/after state, attributable to the individual for SOC 2 / security review.
  • Data boundary — runs through an enterprise LLM endpoint (no training on company data); only the minimum context needed is sent; DLP and retention policies apply.
  • Guardrails — an allow-list of tools, rate limits, and confirmation gates mean the worst case is a proposed action the user declines — not an unintended change.
Net: the copilot sits inside the existing security posture. Identity comes from your SSO, authorization from your existing RBAC, and every change is user-approved and logged — the same controls that govern the user doing it by hand.

12Eval & testing

  • Scoring (unit) — deterministic, so assert exact outputs: a deal closing in 5 days with 21 days no activity must rank #1; a big quiet deal outranks a small one at equal risk.
  • Rules — no-touch-7d and no-meeting-21d must appear on the watchlist; closed-lost/suppressed must never appear.
  • LLM (golden set) — fixed fact sets with expected briefs; grade relevance, ordering, and reason clarity; assert no unsupported claims.
  • News — every signal has a source URL; an item without one is dropped.
  • Copilot — every write tool requires confirmation in tests; the agent never calls a tool outside the registry; permission errors surface cleanly.
  • Guardrails — fuzz with missing/edge data; the brief must degrade gracefully, never crash or fabricate.

Run the eval suite on every change to scoring, prompts, or the tool registry; treat a regression as a blocker.

13Guardrails & security

  • Least privilege — read-only scopes for the daily agent; write scopes only on copilot tools, exercised as the user.
  • Identity from SSO — auth via the company IdP; on-behalf-of tokens; no standing service-account writes.
  • Secrets — in a secret manager / env, never in code or the repo.
  • Grounding — LLM output restricted to injected facts; sources required for news; schema validation with deterministic fallback.
  • Human-in-the-loop — all writes/sends are user-approved; nothing autonomous touches customers or the calendar.
  • Auditability — every flag traces to a record or source URL; every copilot action is logged and attributable.
  • Data handling — minimal PII, short retention, enterprise LLM (no-train), respect suppression / do-not-contact.
